01 The problem

The scoreboard is written by the player.

A bakery announces: “We served 100 customers in one hour.” There is no receipt. The baker kept the books, the books are a spreadsheet, and the baker can edit the spreadsheet at any time.

Four ways that hole shows up

  • 1. Reporting you cannot check. A summary is all you get. There is no path back to the raw measurements.
  • 2. Measurement that flatters. The tool stops measuring exactly when the system is worst.
  • 3. No provenance. Nothing binds the report to who, what, when, or how.
  • 4. Fabrication you cannot see. A generator can emit numbers that were never measured.

In plain words

A load test measures how a system behaves under pressure. Today the same person runs the test and writes the report. The report is not a measurement that was witnessed - it is a claim that was typed.

A student hands in the exam and grades it themselves, with a pencil, on the same sheet. A world record with no referee, no photo finish, no timing system. A scale the market trader carries in their own pocket.

Under the hood

report.json is text. One command turns "p99_ns": 41000000 into "p99_ns": 4100000. Nothing in the file notices. Nothing in the process stops it. The customer has no independent copy of the truth to compare against.

Mainstream tools - k6, Locust, JMeter, Gatling, BlazeMeter, LoadRunner - do throughput and orchestration well, and integrity not at all. The consumer of a report still has to trust the producer.

This matters because performance evidence is used to make expensive decisions - capacity purchases, vendor acceptance, SLA compliance, launch approvals, refunds. Those decisions deserve the same standard of proof we already apply to a tax return or a land title: a record that someone else can independently check.

02 The idea

Commit to the plan, then reveal the evidence.

VeriBench does not ask you to trust a better dashboard. It changes the shape of the artifact. A result becomes three things at once: a plan fixed in advance, a fingerprint that covers every single request, and a seal that only the operator could have produced.

2a
Commit, then reveal

In plain words

Before you measure anything, you write down what you are going to test, where, when and how - and you lock that page. Then you run the test and publish the numbers. Nobody can move the goalposts afterwards, not even by accident.

Under the hood

The run configuration is canonicalised (json-sort-keys-compact-utf8: keys sorted, no insignificant whitespace, UTF-8) and hashed into scenario_hash. The manifest fixes scenario_hash, target.url_origin, run.started_at, the declared method block and the tool identity before the first request. This is the sealed envelope. Everything published later - samples, claims, signature - is bound to it.

2b
A fingerprint tree over every request

In plain words

Every single request gets its own fingerprint. Fingerprints are combined in pairs, going upwards, until one root fingerprint stands for the whole run. Change one byte anywhere and that root changes. One small value protects everything underneath it.

Under the hood

A leaf is one request sample: leaf(i) = SHA-256(0x00 || be64(i) || canonical(sample_i)). Interior nodes are SHA-256(0x01 || left || right). The leaf list is padded to a power of two by repeating the last leaf, and an empty list hashes to SHA-256(""). The result is samples.merkle.root.

2c
A personal seal

In plain words

The whole manifest gets stamped with the operator’s private seal. The stamp proves the operator produced it, and that nothing in it has moved since. Anyone can check the stamp using the public key that travels inside the bundle - no account, no server, no permission needed.

Under the hood

signature.value_b64 = Ed25519_sign(SK, canonical(manifest minus signature)). A 32-byte public key and a 64-byte signature, deterministic and fast, with no parameter choices to get wrong. The public key is embedded, so verification needs no key server and no network. Which key signed is named by key_id = SHA-256(public_key).

The verifier’s checklist

That is the whole idea in one table. Verification is eight checks, all offline, and the verdict is a word plus an exit code - so the same object settles a contract and gates a pipeline.

What verify actually checks, in order
# Check What it establishes Failure label
1 Format The file claims to implement vpmp/v1. FAIL
2 Key binding key_id equals SHA-256(public_key). FAIL
3 Signature Ed25519 over the canonical manifest, minus its own signature. INTEGRITY FAIL: signature
4 Sample count The number of non-empty sample lines equals samples.count. FAIL
5 Merkle root Every leaf is rebuilt and the tree recomputed, then compared. INTEGRITY FAIL: merkle
6 Claims Every published number is recomputed from the raw stream. Integers must match exactly. CLAIM MISMATCH
7 Internal consistency seq strictly increasing; lat_ns == t_end_ns - t_start_ns; times inside the run window; ok == (status < 400). CONSISTENCY FAIL
8 Verdict All of the above pass -> PASS, exit 0. Any failure -> FAIL, exit 1, naming the first failing check. PASS / FAIL

Three of those checks are cryptographic and one is arithmetic, so a bundle cannot be edited after signing without failing check 3, and its raw data cannot be altered without failing check 5. A dishonest operator who wants to publish fake numbers must therefore sign them at creation time - which is precisely the attack that Pillar 3 exists to detect.

And to be clear about what a seal is worth: signing a lie still yields a well-signed lie. Cryptography is the integrity half of the story, not the whole of it - which is why there are three pillars, not one.

03 Why it matters

Disputes become arithmetic.

Performance numbers are already used as commercial promises. VeriBench makes them checkable, which changes what both sides can say in a room.

SLA DISPUTES

“You promised p99 under 200 ms.”

When the vendor’s report and the customer’s monitoring disagree, the argument is about whose spreadsheet wins. With a bundle it becomes a matter of arithmetic: recompute the root, check the signature, read the verdict.

PROCUREMENT

A checkable line in the RFP

A buyer can require a VeriBench bundle as an acceptance artifact, with the exact verification command written into the contract. A vendor who can prove the numbers has an advantage over one who asks to be believed.

TRUST

The bundle is the deliverable

Not a dashboard screenshot, not a PDF rendered by the tool under test. A tamper-evident record with a chain of custody: what was measured, when, under which declared method, and who sealed it.

What a VeriBench bundle does prove

  • Integrity and tamper-evidence. Change the manifest and check 3 fails; change a sample and check 5 fails; change both coherently and you need the private key.
  • Attribution. The bundle was signed by the holder of the key whose fingerprint is key_id, embedded in the bundle.
  • Non-repudiation. An operator cannot later disown a signed bundle, or alter it, without detection.
  • Claim-to-evidence binding. The published summary numbers are forced to equal what the raw sample stream actually says. Lying in the summary is reduced to lying in the raw data, which is a harder and more auditable act.
  • Honesty of the reported distribution. The coordinated-omission correction inputs are part of the signed, Merkle-locked stream, so the correction is auditable rather than a black box.
  • Reproducibility of derived statistics. The percentiles and the bootstrap confidence interval are recomputable from the raw stream under a declared, seeded method.

What it does not prove, stated plainly

  • A valid signature is not proof that packets were sent. A worker can fabricate internally consistent samples and sign them, and checks 3 and 5 will pass. This is the single most important limitation of the MVP, and it is stated here without hedging.
  • It does not establish who the signer is. The public key is embedded, and nothing in v1 binds it to a legal entity or a domain. Key-to-identity binding needs an external certificate authority, or key pinning by the verifier out of band.
  • It does not corroborate server-side latency. The bundle records the client’s view; the server’s own view of the same requests can differ, through queuing in intermediate proxies or clock skew.
  • It does not detect host-level interference. A throttled CPU, a shaped network link, or a co-tenant stealing cycles can be real and invisible to any client-side evidence.
  • It does not protect against a compromised signing host. If the private key and the sample generator are both attacker-controlled, the attacker controls the evidence. The mitigation is hardware key custody, not a change to the bundle format.
  • The confidence interval is conditional on the sample stream. It quantifies sampling uncertainty given the observed samples. It cannot repair a systematically wrong sampling process, and it is not a claim about the future.

04 The three pillars

Sealing is only worth anything if the numbers are honest.

Cryptographic proof of a rigged measurement is proof of nothing. VeriBench stands on three pillars: what was measured, how the latency was counted, and whether the claim survives being attacked.

PILLAR 01

Attested Measurement (VPMP v1)

An Ed25519-signed manifest, bound by a Merkle root to the raw per-request sample stream, with the run configuration committed before the load starts.

In plain words

You write down what you are going to measure, and how, and you lock it. You cannot move the goalposts afterwards - not even by accident, and not even with good intentions.

Under the hood

Addresses failure modes 1 (unverifiable reporting) and 3 (absent provenance). scenario_hash, target.url_origin, run.started_at, the method block and the tool identity are fixed into the manifest first; the samples and the signature come after.

sealed first · cannot be edited after the fact

PILLAR 02

Honest Latency

A stall must not be able to turn itself into a beautiful average by pausing the clock.

In plain words

If the server freezes for two seconds, a closed-loop tool simply stops sending - and therefore stops measuring - exactly when things are worst. The reported percentiles get better as the system gets worse. VeriBench adds the missed schedule skew back, request by request, and signs it.

Under the hood

Addresses failure mode 2 (coordinated omission, Tene 2013). Honest latency is lat_ns + co_extra_ns. Percentiles are nearest-rank over that value; the confidence interval is a seeded bootstrap at 95%. Every unit is an integer - nanoseconds, parts-per-million, milli-requests-per-second - because a float has no single textual rendering, and a producer and a verifier in different languages must agree on the exact bytes.

measured on schedule · correction auditable · error bars included

PILLAR 03

Adversarial-in-the-loop

A second, independent account of the same run - kept by the party that has no reason to flatter the tester.

In plain words

Two books are kept of the same test: what the generator says it sent, and what the target itself saw arrive. The party being tested has no incentive to confirm a fake test. If the two accounts disagree, somebody is lying.

Under the hood

Addresses failure mode 4 (undetectable fabrication). VeriGate’s adaptive difficulty acts as an independent witness: as the generator ramps difficulty, the target counts arrivals and challenge-solve rates, and those observed numbers must agree with the generator’s claimed cadence. The reserved extensions.challenge_response field is where the target’s evidence attaches. Honestly labelled: this is evidence-based suspicion and corroboration, not proof - a colluding generator and target can fabricate both accounts together.

two accounts must agree · raises the cost of the cheat

05 The demo

Three commands, and one byte of sabotage.

The whole story fits in a terminal, which is deliberate: if the proof of a performance claim needs a proprietary viewer, it is not proof.

  1. Keygen

    One Ed25519 keypair. The private key is written with mode 0600 and never leaves the operator’s host; the public fingerprint is key_id.

  2. Run

    The plan is sealed, one sample is streamed per request and never rewritten, then the manifest is signed and the two-file bundle is emitted.

  3. Verify

    Anyone recomputes the tree and checks the signature locally. The verdict is a word, and an exit code: PASS is 0, FAIL is 1.

Honest note. The demo script probes the binary before it starts. If a build does not yet expose the frozen contract, the script says so out loud and emits a spec-conformant bundle from an embedded reference implementation - and in that mode no load is generated and no traffic reaches any target. The verification half of the demo is real either way, which is the half that carries the claim.
