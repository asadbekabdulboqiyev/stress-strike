VeriBench bundle · independent verification

Check the proof yourself. Don’t trust the vendor.

A VeriBench bundle is a claim that a benchmark ran honestly: these samples, these worker commits, these numbers. This page re-computes every one of those claims in your own browser — Merkle roots, inclusion proofs, worker aggregates and Ed25519 signatures. Nothing is uploaded, and there is no server to trust.

    Cryptographic core

    The Merkle inclusion path

    Every worker commits to its samples by publishing a Merkle root over the SHA-256 hashes of the individual samples. Pick any leaf: this page walks the sibling hashes from that leaf up to the root and shows each combination step, exactly as RFC 6962 defines it (leaf = SHA-256(0x00 ‖ sample), node = SHA-256(0x01 ‖ left ‖ right)).

      Disclosure

      Honest numbers: corrected vs. naive

      A load generator that only measures its own send→receive time hides queue waiting time and reports flattering percentiles (this is coordinated omission, Gil Tene’s classic trap). A credible bundle therefore carries both series: the corrected latency and the naive one. Both are re-computed from the samples below, so a vendor cannot quietly publish one set of samples and quote another set of numbers.

      Why the gap matters

      Suppose a client is scheduled to send a request every 10 ms, but the server is slow, so the client is still waiting when the next request is due. Naive tooling waits, then sends — and measures only the short final request, never the 400 ms the client already spent queued. The naive p99 looks healthy; the real experience does not.

      Corrected series restore that hidden waiting time. When you see a corrected p99 far above the naive one, the honest reading is the naive number was hiding pain — not that the tool is broken.

      ◆

      The disclosure itself is verified: if the bundle publishes naive values, this page re-computes them from the same samples and shows whether they match.

      What each edit should break. A single changed sample breaks the Merkle root and the affected worker’s aggregate, and localises to that leaf via its proof. A flipped root nibble invalidates every proof for that worker but leaves other workers intact. A flipped signature byte breaks only the signature — proving the signature is not decoration. Dropping one line breaks continuity, the count and the root.

      Reference

      The bundle format, spelled out

      This verifier is not a black box: the whole contract is written below. Anything that is not fixed here cannot be claimed as verified, and the limitations are listed honestly at the end.

      bundle.json — VeriBench Bundle v1 
      {
  "format": "veribench.bundle",
  "version": 1,
  "suite": "veribench-core-v1",
  "created_at": "2026-10-13T09:00:00Z",
  "hash_alg": "SHA-256",
  "sig_alg": "Ed25519",
  "merkle_alg": "rfc6962-sha256",
  "leaf_canon": "rfc8785-json",
  "metric": { "reported": "co_ns", "naive": "lat_ns", "unit": "ns" },

  "samples": { "file": "samples.jsonl", "count": 51 },
  // "sha256": "64-hex-chars"   optional digest of the samples file

  "workers": [
    {
      "id": "worker-1",
      "sample_count": 20,
      "commit": {
        "merkle_alg": "rfc6962-sha256",
        "leaf_count": 20,
        "merkle_root": "⟨64 hex chars⟩",
        "public_key": "⟨32 bytes hex — raw Ed25519 public key⟩",
        "signature": "⟨64 bytes hex — Ed25519 over commit_payload⟩",
        "commit_payload": "exact UTF-8 text that was signed"
      },
      "aggregate":       { "count":20, "sum":"…", "min":"…", "max":"…", "p50":"…", "p95":"…", "p99":"…" },
      "naive_aggregate": { "count":20, "sum":"…", "min":"…", "max":"…", "p50":"…", "p95":"…", "p99":"…" },
      "proofs": [ { "index": 0, "path": ["⟨hex⟩", "…"] } ]
    }
  ],

  "coordinator": {
    "public_key": "⟨32 bytes hex⟩",
    "signature": "⟨64 bytes hex — Ed25519 over coordinator payload⟩",
    "commit_payload": "exact UTF-8 text that was signed"
  },

  "global": {
    "merkle_alg": "rfc6962-sha256",
    "leaf_count": 51,
    "merkle_root": "⟨root over all leaf hashes, in sample-file order⟩",
    "aggregate":       { "…": "same shape as worker aggregate" },
    "naive_aggregate": { "…": "same shape as worker aggregate" }
  }
}
      samples.jsonl — one JSON object per line 
      {"co_ns":412500,"i":0,"lat_ns":118400,"ok":true,"status":200,"w":"worker-1"}
{"co_ns":233000,"i":1,"lat_ns":198700,"ok":true,"status":200,"w":"worker-1"}
…

w         worker id (must match a workers[].id)
i         0-based index inside that worker, sequential
lat_ns    naive latency, nanoseconds (uncorrected)
co_ns     corrected latency, nanoseconds (the reported metric)
ok        boolean success flag
status    HTTP status code (informational)

Rules
  • Blank lines and lines starting with # are ignored.
  • Two metrics are read: metric.reported (default co_ns) is what the
    aggregates claim; metric.naive (default lat_ns) is the disclosure
    series. If the naive field is absent the page says so instead of
    inventing numbers.
  • Percentiles are nearest-rank over the ascending series:
    index = ceil(p × n) − 1, clamped to [0, n−1].
  • Integers only. A non-finite or non-numeric value is a hard error.
      Canonicalisation + what is signed 
      LEAF CANONICALISATION  (leaf_canon = rfc8785-json)

  leaf_input[i] = UTF-8( JCS( samples[i] ) )
  leaf_hash [i] = SHA-256( 0x00 ‖ leaf_input[i] )
  node(l,r)     = SHA-256( 0x01 ‖ l ‖ r )

  JCS = RFC 8785 JSON Canonicalization Scheme: object keys sorted
  by UTF-16 code unit, no insignificant whitespace, numbers in the
  shortest round-trip form. Because the hash is taken over the
  canonical form of the parsed object, reformatting or reordering
  the keys in the file does NOT change the root — but changing any
  value does.

WORKER COMMIT PAYLOAD  (exact bytes signed by the worker key)

  veribench.commit.v1
  worker=⟨worker id⟩
  leaf_count=⟨n⟩
  merkle_alg=rfc6962-sha256
  merkle_root=⟨64 hex⟩
  metric=⟨reported metric field⟩

COORDINATOR PAYLOAD    (exact bytes signed by the coordinator key)

  veribench.coordinator.v1
  suite=⟨suite⟩
  leaf_count=⟨total⟩
  merkle_root=⟨global root⟩
  workers=⟨id⟩:⟨root⟩,⟨id⟩:⟨root⟩,…

  If commit_payload is present the verifier checks that the payload
  it was given actually contains the declared fields, and then that
  the signature covers it. A bundle may also omit commit_payload, in
  which case the payload above is reconstructed from the fields.
      Verification recipe (what this page does, in order)
      1. Parse samples.jsonl; reject malformed lines with the line number.
      2. Canonicalise every sample (JCS) and hash it into a leaf: SHA-256(0x00 ‖ JCS).
      3. Group leaves per w; check that i runs 0,1,2,… with no gaps and no duplicates.
      4. Rebuild each worker’s Merkle root over its leaves and compare with commit.merkle_root.
      5. Verify every embedded inclusion proof against that root (RFC 9162 §2.1.3.2 algorithm).
      6. Recompute count / sum / min / max / p50 / p95 / p99 for both metrics and compare them field by field.
      7. Rebuild the global Merkle root over all leaves in file order; compare with global.merkle_root.
      8. Recompute the global aggregate from the samples, and separately from the workers’ own declared aggregates — both must agree.
      9. Import each public_key as a raw Ed25519 key and verify the signature over the exact payload bytes.
      10. Report PASS only if every check above ran and passed; skipped checks cap the verdict at PARTIAL.
      Optional offline second opinion. The same verification can be repeated outside a browser with Node ≥ 20, using the identical primitives (crypto.webcrypto.subtle supports Ed25519). If two independent implementations agree, you are no longer trusting either one.
      !

      Limits, stated plainly — so the pass you get is a pass you can defend.

      • This page verifies internal consistency: the numbers really follow from the samples, and the samples really are the ones signed. It does not prove the load was aimed at the right target, that the reported throughput was achievable, or that the samples were not filtered before signing.
      • A bundle signed by one key pair proves authorship by that key — check the key against a published fingerprint before treating it as an identity.
      • Percentiles are re-computed with nearest-rank. A vendor using a histogram estimator will differ slightly in the tail; a mismatch of a few percent on p99 is expected there, and is reported as a plain mismatch rather than an accusation.
      • Very large bundles are bounded by browser memory: samples are parsed in full, and each inclusion proof is re-hashed, so a bundle with millions of samples is slower here than in the CLI.
      • Integers above 253 cannot be represented exactly by JavaScript; the page flags any value that exceeds the safe range.

      Environment

      What this browser can check

      WebCrypto support differs between browsers. This panel is filled in by real feature probes when the page loads — not by a version guess — so you always know exactly which checks ran.

      VeriBench verifier

      A single HTML file. No build step, no npm, no CDN, no backend. Open it from disk (file://), hand it to an auditor, or host it next to the bundle it verifies.

      Cryptography used

      • SHA-256 — leaves, nodes, file digest
      • Ed25519 — worker + coordinator signatures
      • RFC 6962 — Merkle tree shape
      • RFC 9162 §2.1.3.2 — proof verification
      • RFC 8785 — JSON canonicalisation

      Privacy

      Files you drop here are read locally with the File API and hashed locally with WebCrypto. This page makes no network requests of any kind, and stores nothing between reloads.
