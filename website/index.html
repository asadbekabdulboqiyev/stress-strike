Most load tools make you rent their servers and stream your traffic through their pipes. That is not a load test, that is a lecture. stress-strike runs from your hardware, against the real internet, over TLS that looks like a browser.

It does not fake the network. It does not fake TLS. It does not fake the results.

Two ways to run it

Both paths ship the same binaries. Pick whichever fits the hardware you own. The steps below are complete and copy-pasteable.

One machine, everything in containers. Master plus N workers talk to each other over an internal compose network. Your only prerequisite is Docker Desktop already running.

Prereq Docker Desktop (free download), terminal. That’s all.

  1. 1

    Get the code

    A single folder. Works the same on macOS, Linux, and Windows (via Docker Desktop).

    git clone https://github.com/asadbekabdulboqiyev/stress-strike.git
cd stress-strike
  2. 2

    Start the launcher

    It checks that Docker is present, then opens the wizard. With Docker installed it picks path 1 automatically.

    ./scripts/deploy.sh
  3. 3

    Answer four questions

    Target URL, number of workers (1–20), virtual users, duration. Everything else is decided for you.

    target URL to load [http://example.com]: https://shop.example.com
number of workers (1-20) [2]:
virtual users [20]:                  100
duration (seconds) [30]:             120
  4. 4

    Watch it build and run

    First build takes a few minutes while images compile. Then the master starts the run across all workers and streams results to the live dashboard on port 7800.

    building images...  (first build a few minutes)
[ done ] compose file written: dist/docker-compose.generated.yml
[ done ] fleet is up!
  master (gRPC):  localhost:50051   (control plane)
  workers:        4
  target:         https://shop.example.com  (users=100, duration=120s)
  dashboard:      http://localhost:7800
  5. 5

    Stop or rerun, any time

    Change nothing between runs or change everything. Rerunning with new settings takes one line.

    ./scripts/deploy.sh down                         # stop + remove the fleet
./scripts/deploy-docker.sh logs                  # tail all worker logs live
./scripts/deploy.sh -y URL=https://api.example.com WORKERS=6 DURATION=300

Real workers on real Linux hosts. The launcher builds the worker packages for amd64 and arm64, uploads them over scp, installs a hardened systemd unit on each box, and reports back. One VPS is enough; a fleet is just N of them.

Prereq Linux host with SSH + root or passwordless sudo, and an SSH key already authorized. systemd required.

  1. 1

    Authorize your SSH key (once)

    If your key is not already trusted on the host, trust it now. You will only do this once per host.

    ssh-copy-id root@203.0.113.7
  2. 2

    Start the launcher

    Paste your hosts one per line—user@host—and hit enter on an empty line when done.

    ./scripts/deploy.sh
  3. 3

    Answer two questions

    How should workers attach, and a shared token for the control plane. Auto-discovery lets each worker find the master itself; static mode lists workers in the master command.

    How should workers attach to the master?
  1) auto-discovery -- workers find the master themselves
  2) static list    -- master connects to a fixed worker list
mode (1/2) [1]: 1
master address (host:port): 198.51.100.10:50051
protect the control plane with a shared token? [y/n]: y
token (any secret string): ****************
  4. 4

    Watch each host install itself

    The package build runs once, then every host gets the worker uploaded and installed in about 30 seconds. Systemd keeps it alive across reboots.

    building worker packages v0.11.0 (amd64 + arm64)...
▬▬ deploying to 2 host(s) ▬▬

[1/2] root@203.0.113.7
      arch: amd64
      uploading worker package + helpers...
      [ ok ] worker installed, systemd unit active (running)
[2/2] root@203.0.113.15
      arch: arm64
      uploading worker package + helpers...
      [ ok ] worker installed, systemd unit active (running)

▬▬ fleet ready -- 2 worker(s) ▬▬
  5. 5

    Drive the fleet from your control box

    The launcher prints the exact master command for your setup. Static mode needs one more flag; auto-discovery just works. Confirm with the 6–second smoke test.

    stress-strike-master -listen 0.0.0.0:50051 \
  -wait-workers 2 -wait-timeout 30 \
  -url https://target.example.com -users 500 -duration 120 \
  -token secret \
  -tls-fingerprint chrome -timeline -quiet

    Smoke test right after the master is up:

    stress-strike-master -wait-workers 2 -wait-timeout 30 \
  -url https://example.com -users 8 -duration 6 \
  -token secret \
  -tls-fingerprint chrome    # expect 0 errors

Compare the paths

Which path fits you

Both produce identical workloads and identical numbers. The difference is where the workers live.

Question Path one — Docker Path two — VPS fleet
Need Docker Desktop a Linux host with SSH + systemd
Workers live containers on one machine on each real server
Scale 1 machine, its limits as many hosts as you own
Time to first run a few minutes (first build) about 30s per host
Traffic really leaves your box yes, from one IP yes, from every host you add

FAQ

Same rules as any load tool: only run against infrastructure you own or are explicitly authorized to test. The tooling does not care where you point it. The terms of your target do. Read the LICENSE and use common sense.

Possibly. stress-strike speaks real TLS with browser fingerprints (chrome, firefox, ios among others), so it passes most setups, but a strict WAF can still drop sustained streams. If a run fails at high rates, drop to a smaller run, try a different fingerprint, or check the timeline.

Path one needs Docker Desktop and a terminal, nothing else. Path two needs basic SSH familiarity, but the launcher handles the install entirely and prints friendly instructions when something is missing (for example, the ssh-copy-id hint).

Those either fake TLS or run from someone else’s datacenter. stress-strike runs from hardware the tester controls, over browser-grade TLS, and can span many of them at once. The results are your network to your target, no middleman in between.

The Docker path works on Windows via Docker Desktop. The fleet path assumes a POSIX shell on the control machine, so pair it with WSL or run the launcher from any Linux/macOS box and target the same hosts.
